## Датасет вкратце

`ml` содержит **10 CSV** под `data/` (2 700 строк суммарно) плюс зеркала
`Housing_Data.sql` (500 INSERT) и `Customer_Churn.json` (800 записей). Одна строка = один
объект: клиент (`Customer_Churn`), дом (`Housing_Data`), пользователь (`Social_Network_Ads`),
компания (`50_Startups`), наблюдение препроцессинга (`Data*.csv`). Временной колонки нет
ни в одном наборе. Качество данных в целом **хорошее**: 0 полных дублей в крупнейших
наборах, 0 пропусков вне `Data*.csv`, все категории и диапазоны валидны. Основной риск —
не «грязь», а синтетические артефакты генератора (детерминированные производные признаки
и сконструированная коллинеарность).

## Топ проблем качества

### Проблема 1: `TotalCharges` — детерминированная производная, а не признак
- **Что:** `TotalCharges == MonthlyCharges × (TenureMonths + 1)` выполняется для
  **800/800** строк `Customer_Churn.csv`.
- **Влияние:** столбец дублирует информацию `MonthlyCharges` + `TenureMonths`; в линейных
  моделях даёт коллинеарность и вводит в заблуждение (corr с `MonthlyCharges` всего 0.33,
  но тождество точное). Риск «случайного» использования как независимого сигнала.
- **Действие:** исключить из признаков линейных моделей либо явно пометить как
  engineered feature в документации проекта.
- **Владелец:** аналитик / дата-инженер.

### Проблема 2: `Bedrooms` детерминированно выведен из `SquareFeet` (коллинеарность)
- **Что:** `Housing_Data.csv`, r(`SquareFeet`, `Bedrooms`) = **0.894**; r(`SquareFeet`,
  `Price`) = 0.951; r(`Bedrooms`, `Price`) = 0.878. Генератор строит `Bedrooms` из `sqft`.
- **Влияние:** классическая мультиколлинеарность — коэффициенты линейной регрессии
  нестабильны, интерпретация знаков ненадёжна.
- **Действие:** для линейной модели оставить одну из пары (`SquareFeet`) или проверить VIF;
  для деревянных моделей — оставить обе.
- **Владелец:** аналитик.

### Проблема 3: `Price` зажат на полу 50 000 $ (структурный sentinel)
- **Что:** 2 строки из 500 (0.4%) имеют `Price == 50 000` — результат `max(50000, price)`
  в генераторе.
- **Влияние:** эти значения — не реальный сигнал, а нижняя граница (усечение). Могут
  слегка смещать оценку для дешёвого сегмента.
- **Действие:** классифицировать как структурный sentinel, **не удалять**; при
  необходимости отметить флагом. Доля мала, влияние ограничено.
- **Владелец:** дата-инженер.

### Проблема 4: `Data_large.csv` — 2 полных дубля + 52 пропуска
- **Что:** 400 строк, 2 полные дубликаты (0.5%), 52 пустые ячейки `Age`/`Salary` (~8%).
- **Влияние:** дубли — следствие дискретного пространства признаков (низкая цена ошибки);
  пропуски намеренные (генератор оставляет ~8% для работы `SimpleImputer`).
- **Действие:** дубли разобрать (оставить — риск мал); пропуски оставить как есть —
  это вход для имputатора, задокументировать ожидаемую долю.
- **Владелец:** аналитик.

### Проблема 5: `Id` / `CustomerID` / `User ID` — ID-колонки с высокой кардинальностью
- **Что:** `Id` 500/500, `CustomerID` 800/800, `User ID` 400/400 уникальных значений.
- **Влияние:** если подать в модель — ложный сигнал и переобучение.
- **Действие:** исключить из признаков (в проекте уже не подаются — столбцы вне
  `NUMERIC_COLUMNS`/`CATEGORICAL_COLUMNS`).
- **Владелец:** аналитик.

## Что в порядке

- `Customer_Churn`, `Housing_Data`, `Social_Network_Ads` — **0 полных дублей**, 0 пропусков.
- Все категориальные колонки содержат только ожидаемые значения (3 страны, 3 штата,
  3 контракта, 3 типа интернета, 2 пола) — неожиданных категорий нет.
- Числовые диапазоны валидны: `Age` 18–75, `MonthlyCharges` ≥ 0, `Price` ≥ 0, цели
  `Churn`/`Purchased` строго ∈ {0,1}.
- Зеркала согласованы: `Customer_Churn.json` == CSV (800×9, `.equals` True);
  `Housing_Data.sql` = 500 INSERT = 500 строк CSV.
- README-метрики воспроизведены: **21 тест**, **Train (8,5)/Test (2,5)**, **400/300/500/800**
  строк, leakage-free fit on train split, **11 PNG** при dpi=300.
- Доминирующий сигнал устойчив и не композиционный: контрактный разрыв churn (×15.8)
  не объясняется разным распределением тенуре между контрактами.
